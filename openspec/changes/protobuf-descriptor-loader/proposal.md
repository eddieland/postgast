## Why

**Status: deferred.** Not approved, not scheduled. This exists so the research behind it is not lost. It depends on
`protobuf-runtime-compat` landing first, and it does not fix anything that change does not already fix.

`src/postgast/pg_query_pb2.py` is protoc gencode, and gencode is version-gated against the protobuf runtime
(`_runtime_version.ValidateProtobufRuntimeVersion`). The gate is one-directional — the runtime may not be older than the
gencode — so it constrains the declared floor and nothing else.

The consequence is a standing maintenance hazard rather than a bug: every `make proto` run on a newer protoc raises the
version postgast's users must have, silently, as a side effect of regenerating a file nobody reads. That is exactly how
`protobuf-runtime-compat` came to exist. That change makes the next occurrence a red CI leg; this one would remove the
coupling altogether.

postgast never needs gencode semantics. It parses bytes produced by libpg_query's protobuf-c encoder and hands back
message objects; the C side owns the wire format, and the Python side only needs classes matching the vendored schema.
Message classes can be built from a serialized descriptor with public runtime APIs, which no version gate covers.

## What this is worth, honestly

The only user-visible gain is a lower floor. A prototype loader was verified working on protobuf **4.25.8, 5.27.2,
5.28.3, 5.29.6, 6.33.1** — 1432 names and a correct roundtrip on each. So this change is worth doing **only if postgast
wants to declare a floor near `protobuf>=4.25`**.

If the floor stays at 5.29, this change replaces ~100 KB of generated code with a hand-written module plus a ~100 KB
binary descriptor and produces an identical support matrix. Decide the floor question first; the implementation follows
from the answer.

Secondary gains, both real but small: releases stop being coupled to the protoc that built them, and the module stops
registering in the default descriptor pool (see the isolated-pool decision in `design.md`).

## What Changes

- Replace protoc gencode with a hand-written `pg_query_pb2.py` loader that builds message classes at import from a
  committed `src/postgast/pg_query.desc` serialized `FileDescriptorSet`.
- Build into a private `DescriptorPool`, exposed as `pg_query_pb2.DESCRIPTOR_POOL`.
- Change `make proto` from `--python_out` to `--descriptor_set_out --include_imports`, still emitting `--pyi_out`.
- Lower the declared floor to whatever the loader supports and CI verifies.

## Impact

- `src/postgast/pg_query_pb2.py` — replaced: 744 lines of gencode become a short loader (no longer generated)
- `src/postgast/pg_query.desc` — new: ~100 KB serialized `FileDescriptorSet`, shipped as package data
- `src/postgast/pg_query_pb2.pyi` — unchanged in content, still generated by `protoc --pyi_out`
- `pyproject.toml` — floor lowered; `pg_query_pb2.py` dropped from the ruff/basedpyright/codespell/coverage excludes
- `Makefile` — `proto` target switches to `--descriptor_set_out --include_imports`
- `.gitattributes` — `pg_query_pb2.py` no longer `linguist-generated`; `pg_query.desc` marked binary
- `.github/workflows/ci.yml` — the `protobuf-compat` floor leg picks up the lowered floor automatically
- `scripts/generate_nodes.py` — affected; see the bootstrap defect in `design.md`
